# Elegantia — エレガント品質達成カタログ
作成: 2026-09-11 / 状態: 設計提案・未実装・未検証
対象: アクションゲーム、3DCG制作（モデル・リグ・アニメーション・映像・合成・納品）、高品質グラフィックス。
3DCGはリアルタイム表示とオフラインレンダリングの双方を含む。静止画、映像、対話コンテンツ、制作ツールで適用範囲を宣言し、発話・音響・ネットワーク・VR/ARなどは採用した機能だけを評価する。
L01〜L40は3DCG制作工程と作品の成立性、G01〜G50は最終画の表現・描画品質を主に扱う。両方が適用される項目も平均点で相殺しない。
D01〜D20はジャンルを問わないゲーム全般の成立性（目的、ループ、ルール、経済、現実連動、権限、課金、配信）を扱い、A01〜A45のアクション固有要件と重ねて適用する。
P01〜P20はキャラクターの実在性（同じ空間に居る、働きかけに応える、同じ個体として続く）を扱う。飼育・同行・AR配置など、キャラクターとの関係が体験の核となる作品で適用し、L・Gの造形・描画要件を代替しない。

## 品質の姿勢
『ガンダムW』の公式紹介は、トールギスIIの戦いを騎士道とエレガントさに結び付けている。[公式紹介](https://www.gundam.info/news/goods/news_goods_20110825_5987p.html)
ここからElegantiaへ持ち込むのは私の設計上の解釈であり、作品の公式な品質定義や台詞の引用ではない。
- 成果だけでなく、そこへ至る振る舞いにも美意識を通す。
- 操作する人、制作する人、見る人に、作り手側の都合や整理不足を押し付けない。
- 応答、情報、映像、音、間、失敗からの復帰まで一つの意図で整える。
- 豪華さを足すほど、誰を見せたいのか、何をしてほしいのかが鮮明になる。
- 違和感を認識したら「動くからよい」で通さず、最後まで仕上げる。
AIにも同じ基準を適用する。数を埋める指摘、根拠のない断定、待ち時間の放置、利用者への判断の丸投げを品質不良として扱う。

## 「標準以下を排除」の判定
判定は総合点の平均で通さない。適用される必須要件が一つでも未達なら不合格、証拠がなければ未確認とする。
成立性・安全性・一貫性の要件は必須の入口であり、不具合がないだけでは「標準超え」と判定しない。

1. 比較する同ジャンル・同価格帯・同出力条件の作品と、評価場面を評価前に固定する。都合のよい古い比較対象だけを選ばない。
2. 体験評価を「0:破綻 / 1:標準未満 / 2:標準相当 / 3:明確に上質 / 4:作品固有の魅力」に固定する。
3. 応答・理解・操作/鑑賞の快適さ・表現の一貫性・復帰の各適用軸が3以上であること。軸を平均して2以下を隠さない。
4. 作品の核となる場面は4を要求する。「何が良いか」を時刻付き映像と具体的な体験差で示す。
5. 初期の社内判定案は評価者5人中4人以上が3以上とし、標準相当以下の理由は全件記録して再現・切り分けする。この人数は統計的な一般保証ではなく、後に対象ユーザーと試行数を拡張する。
6. 自動計測の合格と、実機・実時間の体験審査の合格を両方要求する。AI単独で美意識の最終合格を確定しない。
7. N/Aは機能非採用の場合だけ。難しい・未実装・予算不足をN/Aの理由にしない。対象外にするなら製品の提供範囲も明示的に変更する。
8. 「観測した不具合0件」は定義した評価範囲内の結果。未観測の全状態を含む完全無欠の保証には使わない。

## 共通の評価条件・数値案
以下はElegantia向けの厳しめの初期設計目標。業界共通の規格値と混同しない。製品採用前に対象機材・演出意図・比較作品を基に確定する。
値や評価範囲が未確定の項目を合格にしない。対応機種を減らす場合も、低品質のまま対応を称しない。

| 記号 | 評価条件・初期目標 |
|---|---|
| T | 実レンダリング周期。60fpsなら16.67ms、120fpsなら8.33ms。フレーム生成後の表示fpsとは別に記録する。 |
| P | 最低対応・推奨・最高設定の各端末/解像度/出力/入力機器の組。設定、OS、ドライバー、電源、熱状態も保存する。 |
| F | リアルタイムの重負荷場面でCPU/GPU処理時間を別計測しp99≦0.8Tを目標とする。操作中の未承認の2T超停止0回。オフライン最終レンダーにはfps予算を課さずOを適用し、完成映像の欠落・重複フレームは別に検品する。 |
| I | 物理入力→画面の最初の有効な反応を外部計測。ローカル60fps系はp95≦50ms、120fps系はp95≦30msを初期目標。意図した攻撃の予備動作と受付遅延を分離する。 |
| U | UI受付表示p95≦100ms、ローカル頻用画面の利用可能化p95≦200ms。長い処理は状態・中断・復帰を提供し、偽の進捗を出さない。 |
| L | 3DCGの対話プレビューでは入力・パラメータ確定→有効な表示更新p95≦100msを初期目標とする。モーション取込を使う場合は取得→CG出力p95≦50msを別計測する。最終レンダーの所要時間を入力遅延と混ぜない。 |
| O | オフライン処理は代表・最大負荷ショットの解像度、尺、サンプル数、品質条件、端末を固定し、処理時間・ピークメモリ・ストレージ上限を事前合意する。予算と画質を両方満たし、全納品フレームの欠落・重複・破損0件。 |
| AV | 音を伴う完成映像で音画の時刻差の絶対値≦20msを初期目標とし、先行/遅延を符号付きで保存する。演出上の意図的なずれは対象と理由を別に記録する。静止画や音を持たないモデル納品には適用しない。 |
| R | ゲームの死亡確定→再操作p95≦2秒を初期目標。演出スキップ設定、初回/反復、ディスク状態を明記する。 |
| N | ネットワーク評価例: RTT 0/30/80/150ms、ジッタ0/20ms、損失0/1/3%、切断・再接続。通常保証範囲と劣化時の保証を先に宣言する。 |
| V | 静止画は最終サイズと必要な拡大・縮小、映像は通常速度・低速・パン・急旋回・カット、モデルは利用先の画角と動作範囲で評価する。逆光・暗所・透過重なり・最終圧縮も確認し、主役・文字・重要手掛かりを優先する。 |
| H | 対象ユーザーの初見・習熟後、必要なアクセシビリティ条件で観察する。標準超えの判定は上の比較審査に従う。 |
| S | 継続利用の設計例: ゲーム・対話制作は2時間以上、オフライン処理は最大予定バッチの完了まで。冷起動・初見アセット・暖機後・最大シーン・連続切替・保存再開を含める。試行数、全失敗、最大値を記録する。 |
| E | 不具合再現場面と境界条件を事前登録。記録するものはビルド、アセット版、設定、機材、入力、状態遷移、フレーム時刻、映像、音、欠測。観測器自身の負荷も測る。 |

画質の数値閾値や接触の許容誤差は、被写体サイズ・画角・出力ピクセル・キャラクター寸法に依存する。例えば「足滑り1cm以下」だけで合格させず、寄りの画角で見える違和感もVで判定する。
「比較」「自然」「明瞭」と書いた要件は、対象クリップとH/Vの評価表を結び付けること。以下の全行にP・Eおよび適用される共通条件を継承する。
